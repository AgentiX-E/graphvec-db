### 背景
承接 2026-08-24 的 List11 [3] 修复（提交 `190ba071`），本轮继续攻坚「UNWIND 管道 + RETURN 顶层聚合」的 TCK 失败，目标让 Aggregation 系列转正。

### 三层根因（全部在 `src/query/executor-unwind-pipeline.ts`）

1. **Step 4 入口条件过严**
   - 旧：`plan.aggregate && !plan.with?.columns?.length`
   - 问题：`WITH [1,2,3] AS xs UNWIND xs AS x RETURN count(x) AS n` 里，`with.columns` 非空（列表字面量投影），误判为「聚合已处理」，Step 4 被跳过 → 返回 3 行 `[{n:1}×3]` 而非单行 `[{n:3}]`。
   - 修复：`_step4Eligible = _hasUnwind ? !_withHasAggCol : !plan.with?.columns?.length`
     - 仅 UNWIND 场景走新逻辑；`_withHasAggCol` 检测 `with.columns` 里是否真有聚合列（`/^\s*(collect|count|sum|avg|max|min)\s*\(/i`）。
     - 无 UNWIND 场景保持原行为（避免破坏 `WITH 1 AS a, 2 AS b RETURN collect([a,b])` 字面量 builder，该场景 `plan.aggregate` 但非跨行聚合）。

2. **输出键名不匹配**
   - 无 alias 的 `RETURN max(x)`，parser 把 `agg.alias` 设成 `max`（去掉 `(x)`），但 `returnColumns[0]` 是完整 `max(x)`。
   - TCK 期望 `{"max(x)": "2"}`，实际返回 `{"max": 2}`，`normalizeActual` 用 key `max(x)` 查不到 → `null`。
   - 修复：`_rc0IsAgg`（`/\w+\s*\(/` 匹配 `returnColumns[0]`）时优先用 `returnColumns[0]` 作为输出键。

3. **max/min 只支持数字**
   - 旧：`Number()` 过滤 + `Math.max/min`，字符串/列表/混合类型全变 NaN → 0。
   - 修复：新增 `_aggCompare` + `_aggTypeRank`（list=0 < string=1 < boolean=2 < number=3，符合 Cypher 值层次），支持同类型（数值序、字符串/列表字典序）与跨类型比较；空集返回 null。

### 关键教训（重要！务必记住）

1. **`_orderByTypeRank` 绝不能乱改**
   - 第一版直接改全局 `_orderByTypeRank`（原 `boolean=0<string=1<number=2<list/map=50` → 新 `list=0<string=1<boolean=2<number=3`），让 Aggregation2 转正，但引入 with-orderBy **4 个回归**（[21]/[22] distinct types、[15]/[16] time expression）。
   - 根因：`_orderByTypeRank` 的 `default: 50` 把 map/node/rel/list/path 等结构类型都归一类，无法区分（权威层次是 MAP<NODE<REL<LIST<PATH<<...<STRING<BOOLEAN<NUMBER）；且它是全局 ORDER BY 排序函数。
   - **解决**：回退 `_orderByTypeRank`，改用**局部** `_aggCompare` 只影响聚合 max/min，零回归。

2. **Cypher 权威值层次**（Neo4j 官方 ordering-equality-comparison 文档）
   - 从最小到最大：MAP < NODE < RELATIONSHIP < LIST < PATH < VECTOR < POINT < temporal(ZONED DATETIME/LOCAL DATETIME/DATE/ZONED TIME/LOCAL TIME/DURATION) < STRING < BOOLEAN < INTEGER/FLOAT；null 排最后。
   - 聚合 max/min 需遵循：list 最小、number 最大（Aggregation2 [11]/[12] 期望 `min=[1,2]`、`max=1`）。

3. **并发 cucumber 污染**
   - 同时跑多个 cucumber-js 进程会互相干扰（`_geInstanceRegistry` 缓存 GE 实例残留），导致 MatchWhere/Comparison3 出现「假回归」。
   - 一度误判 Comparison3:33/:51 为真回归，单独重跑即恢复。**必须串行跑，或跑前 pkill 清理**。

4. **bash 反引号陷阱**
   - commit message / shell 命令里用反引号 `` ` `` 会被 bash 当命令替换，导致代码片段被吃掉。改用 `git commit --amend` 重写 message（去掉反引号，用普通文本表达）。

## WITH 聚合投影（count/sum/avg/max/min 计算缺失）修复完成 ✅（提交 `9fc2f4b5`，Lambertyan）

### 根因
Step 3（`executor-unwind-pipeline.ts` 的 WITH 投影聚合逻辑）对聚合列只做「收集原始值到 `ac.rows` 数组」，然后 `aggRow[alias] = ac.rows`（整个数组）。这对 `collect` 正确，但对 count/sum/avg/max/min 错误（它们需要实际计算）。

### 修复
1. `aggCols` 结构扩展 `{ alias, fn, rows }`，`fn` 从 `col.expression` 提取聚合函数名（collect/count/sum/avg/max/min）。
2. 新增 `_computeAggregate(fn, rows)` 按函数分派：
   - `collect` → 原始数组（不变）
   - `count` → 非 null 计数（`count(*)` 每行 push 字面量 1，length 即行数）
   - `sum`/`avg` → 数字累加（跳过 null）
   - `max`/`min` → 复用 `_aggCompare`（Cypher 值层次）

### 验证
- 单元测试 `return-collect-aggregation.spec.ts` **25/25**（新增 8 个 WITH 聚合测试：count/count(*)/count-null/sum/sum-null/avg/max-min/collect 回归）
- quick 回归 4/4 全绿
- 表达式 TCK 192→192 零回归
- clauses/with 5/29（failed 24，与旧基线一致）
- with-orderBy 272/292（failed 20，与旧基线一致）

### 关键认知
- **TCK 里没有 `UNWIND ... WITH count(x)` 场景**（openCypher 的 WITH 聚合都是 `MATCH...WITH` 走 GE 路径，单独的 WITH 聚合投影在 UNWIND 后罕见）。因此本修复的验证依赖单元测试（25/25），TCK 仅验证零回归。
- 诊断证明修复真实有效：`WITH [1,2,3] AS xs UNWIND xs AS x WITH count(x) AS c RETURN c` 从 `[{c:[1,2,3]}]`（broken）→ `[{c:3}]`（正确）。

## Precedence 6 场景诊断结论（2026-08-25 23:30 GMT+8）— 不修复，属 TCK 边界不一致

### 诊断过程与铁证

1. 精确定位：Precedence1.feature 实际失败的是 **[20]（line 324/325，`=`/`<>`）+ [22]（line 381-384）共 6 个**。[19]/[21] 已 PASS（用 `any()`，语义宽松）。

2. 根因逐层排除：
   - `_evaluateExpression('(NOT (a = b)) = ((NOT a) = b)', {a:null,b:null})` → **null**（正确三值逻辑：`NOT null = null`、`null = null = null`）
   - `collect((NOT (a = b)) = ((NOT a) = b))` → `[true,true,null,true,true,null,null,null,null]`（**5 true + 4 null，无 false**，收集正确）
   - `all(x IN eq WHERE x)` → **null**（当前实现：`nullCount>0 且无 false → null`）

3. **权威对照（决定性）**：Quantifier4.feature [10]「All quantifier on lists containing nulls」明确 `all([2,null] WHERE x=2) → null`、`all([null,2] WHERE x=2) → null`。这与 [20] 的「含 true + null 无 false → 返回 null」**完全一致**，Quantifier4 当前 103/105（仅 [8]/[9] 节点/关系类型失败，与三值逻辑无关）。

### 结论

Precedence [20]/[22] 期望 `all(...) = true`，但其 `eq` 列表必然含 null（`null = null → null` 三值逻辑），而 `all()` 的权威语义（Quantifier4 充分覆盖）对含 null 的列表返回 null。

**这是 openCypher TCK 自身的边界不一致**：[20]/[22] 的期望值 `true` 与 Quantifier4 的 `all()` null 语义数学上不可调和。

### 不修复的原因（与之前 summary 记录一致，且本轮有更精确证据）

任何让 [20] 返回 true 的改动（改变 `all()` 过滤 null、或改变 `null = null` 三值逻辑）都会破坏 Quantifier4 的 103 个通过场景，引发大规模回归。这是「改变 null 语义引发大规模回归」的典型。

### 后续建议

- 这 6 个场景不应通过改 `all()`/`null = null` 语义来「修复」，应在 TCK 层标记为「known incompatibility」或从断言中豁免（但项目规则禁止改 TCK 数据）。
- 真正的 next 方向应是：with-orderBy 剩余 20 失败、或 Aggregation3/6/8 的 UNWIND 聚合（`count(DISTINCT)`、`sum` over range 等，这些是**真 bug**，非 TCK 不一致）。
