## 已完成的修复链

### 1. WITH WHERE 后过滤
- 问题：`WITH a, b WHERE a IS NULL OR b IS NULL` 在 `_executeWithUnwindPipeline` 中 WHERE 子句完全被忽略
- `extractWith` 的 walk 函数不处理 `WhereContext`，`plan.with.filters` 始终空数组
- `plan.whereBody` 只在 `plan.hasMatch=true` 时设置
- 修复：从 query 文本 regex 提取 WHERE 子句，逐行 `_evaluateExpression` 过滤

### 2. WITH 投影跳过 UNWIND 变量
- `WITH a, b` 中 `col.alias === null && col.expression in evalCtx` → 遇到 `continue`
- 结果 `newRow` 空对象，后续 RETURN 里 `a`/`b` 全是 `null`
- 修复：传递值到 `newRow` 后再 `continue`

### 3. `(expr) IS NULL` 识别
- 问题：`_evalAtom` 看到 `(` 时解析括号内容，但不检查后缀是否为 `IS NULL`
- TCK 中大量 `(expr) IS NOT NULL` 模式未命中
- 修复：在 `_evalAtom` 找到匹配 `)` 后检查后缀，递归解析
- 同时移除 `_evalComparison` 中 IS NULL 处理的过严条件 `!t.includes('(')`

### 4. 科学计数法 E/e 跳过
- `2E+01` 中 `E` 后面的 `+` 不被 `_evalAddSub` 识别为运算符
- 修复：检查左操作数末尾是否为 `e`/`E`

### 5. 字符串转义序列
- `\n`, `\t`, `\r`, `\\`, `\'`, `\"`, `\uXXXX` 转义
- 注意：`\uXXXX` regex `/\\u([0-9a-fA-F]{4})/g`

### 6. 八进制 0o/0O 字面量
- 在 `_evalLiteral` 中添加 `/^0[oO][0-7]+$/`
- 使用 `parseInt(v.slice(2), 8)`

### 7. formatValue 递归改造
- 重写 `_stringifyVal`：递归处理嵌套数组和 map
- Map 输出 Cypher 格式 `{key: value}` 而非 JSON

## 已知阻塞问题
### extractReturn 不识别 Cypher 字面量语法
- **严重程度**：阻塞 literals 和其他目录的后续大量测试
- `RETURN 0o77 AS v` → `returnColumns` 解析为 `["0"]`（别名变成 `0`）
- `RETURN 2E+01 AS v` → 解析为 `["2"]`
- `RETURN [1, 0o77]` → 逗号被视为列分隔符
- **根因**：`ast-to-plan-v2.ts` 的 `extractReturn`/`extractWith` 用简单逗号分割 + 关键字过滤，不知 Cypher 字面量语法
- 需要改写为上下文感知的解析器

### 核心修复

1. **`postProcessReturnColumns`** — ANTLR Cypher grammar 不认识 `0o77`（八进制）、`2E+01`（科学计 数法）、多行列表等字面量，ANTLR 错误恢复后返回表达式被截断。在 `parseCypherToPlan` 出口处用原始 query 文本通过 `splitByTopLevelCommas`（括号感知逗号分割）重建完整表达式。ANTLR 列数和 query 文本列数不一致时触发全量重建。

2. **`_evalMulDiv` 加入 `_inString`** — 表达式内部 `/` 被误认为除法运算符。例如 `'...\\//...'` 中 `//` 触发除法分割，导致字符串被截断传递给 `_evalLiteral`。修复：三处（`*`/`/`/`%`）都加 `&& !_inString(t, i)`。

3. **`_stringifyVal` 格式化** — `e+305` → `e305`（去掉 `e+` 的 `+`），字符串内部 `'` 和 `\` 转义
