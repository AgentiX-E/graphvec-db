## 2026-09-02 — precedence 目录修复（6→0）+ collect null 语义澄清

### 本轮根因与修复（进行中，尚未提交）

**目标**：precedence 目录 6 个失败清零。

**核心根因链**（诊断确认）：
1. `all(x IN [true, null] WHERE x)` 走了 `_evalBinary` → `_tryFnCall` → `_builtinFunctions.all` → `_evalListPredicate`（line 1275），该实现是**标准三值逻辑**：`[true, null]` → null。
2. `_evalAtom`（line 3701）里的 listPredMatch（line 3884）有"跳过纯变量 null"逻辑（`if (val === null && condExpr === varName) continue`），语义正确但**成了死代码**（`all(...)` 函数调用在 `_evalBinary` 层就被 `_tryFnCall` 拦截，不会下沉到 `_evalAtom`）。
3. precedence [20]：`collect((NOT (a=b)) = ((NOT a)=b)) AS eq RETURN all(x IN eq WHERE x)`，eq 含 null（4 true + 5 null），期望 true。

**关键语义判定（来自 TCK 反推）**：
- `all(x IN [2, null] WHERE x = 2)` = null（Quantifier4 [10]，非纯变量条件，null 元素 → null，标准三值逻辑）。
- `all(x IN [true, null] WHERE x)` = true（纯变量条件 `WHERE x` + null 元素 → **跳过**，precedence [19][20] 依赖）。
- 差异在条件是否为**纯变量引用**（`condExpr.trim() === varName`）。

**修复（`_evalListPredicate` line 1288 循环内）**：对 `all` 类型，当 cond 为 null 且 `whereClause.trim() === varName` 时 `continue` 跳过（不计入 nullCount）。注释英文。

### collect null 语义澄清（重要教训）

一次错误尝试：把 `collect` 从"过滤 null"改成"保留 null"，导致 **Aggregation8 [3][4] 引入 2 个新失败**。

**正确 Cypher 语义**（决定性证据）：
- `collect(x)` 未绑定变量（OPTIONAL MATCH 无匹配）→ `[]`（过滤 null，Aggregation5 [1]）。
- `collect(DISTINCT x)` where x ∈ [null,null] → `[]`（过滤 null，Aggregation8 [3]）。
- `collect(DISTINCT x)` where x ∈ [null,1,null] → `[1]`（过滤 null，Aggregation8 [4]）。
- **结论：`collect` 无论 distinct 与否都过滤 null**。已恢复 `executor-unwind-pipeline.ts` 两处 collect 的 `.filter(v => v !== null && v !== undefined)`，仅把注释改为英文准确描述。
