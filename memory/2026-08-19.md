## 2026-08-19 中午 — 节点属性键序非确定性根因确认（续）

### 新增提交 a1312a02（已推 origin/master）
- InvalidAggregation（ORDER BY 聚合）检查，executor-validate-plan.ts。
- 语义：ORDER BY 里的聚合函数仅当调用文本与 WITH 投影表达式完全匹配时合法，否则抛 InvalidAggregation。
- 验证：WithOrderBy2 [25] 25 个 example 全转正；WithOrderBy4 [16] 仍合法（其残留失败是 avg() 空集返回 [null] 而非 null，属聚合求值独立 bug）。
- quick 回归 4/4 全绿。

### 键序非确定性根因（已彻底确认）
- ✅ **根因**：OverGraph（Rust 原生库）持久化（flush/close 后重新打开）时，节点 props 键序丢失且**非确定**。
  - 验证：`diagStorage.ts` — 不同 GE 实例开同一 path，`_executeQueryPlan` 读出的 props 键序随机（`_label,num,text` / `text,_label,num` / `num,_label,text`）。
  - 同一 GE 实例内（内存缓存 + 未 flush）稳定；flush 到磁盘后 Rust HashMap 序列化丢序。
- ✅ **定位链**：`_executeViaGraphEngine` → `ge._executeQueryPlan`（graph-engine.ts:1631）→ `_scanAll`(:2422) → `getNode`(:653，LRU 缓存) → `storage.getNode`(overgraph-storage.ts:525) → `_deserializeProps` → `this._db.getNode`(= OverGraph.open Rust)。
- ✅ **序列化点**：step-definitions.ts `toNodeNotation`(:236) 用 `Object.keys(obj)` 顺序输出属性，忠实复制已乱序的 keys → 属性顺序内嵌进 notation 字符串 → TCK `in any order` 用 JSON.stringify 比较 → 随机失败（flaky）。
- ✅ **msgpackr 保序**：`msgpackr` 的 encode/decode 完美保留键序（实测 num,text,_label 和 zeta,alpha,mid 均保序）。
- ✅ **已有机制**：overgraph-storage.ts 已有 `_serializeProps`/`_deserializeProps`（用 `__c` key 存 msgpack number[] blob），但**默认 `_compress=false`/`_compressionStrategy='none'` 不启用** → props 裸对象传给 Rust → HashMap 丢序。

### TCK 期望顺序 = CREATE 声明顺序
- 关键证据：`WithSkipLimit1.feature:66` `CREATE (a {name: 'A', num: 0, id: 0})` 期望 `({name: 'A', num: 0, id: 0})` — 这是**非字典序**（name < id 字典序应为 id 在前？实际 i<n，id 应排 name 前，但 TCK 期望 name 在前 = CREATE 声明顺序）。
  - 等等：name/n/i 字典序 i(105) < n(110)，所以字典序 id < name，但 CREATE 是 name 在前 → 确认**非字典序**，TCK 期望**严格 CREATE 声明顺序**。
- 所以正确的修复必须**保留 CREATE 声明顺序**（不能简单用字典序稳定化）。

### 修复方案（未决定，待评估）
- **方案 A（存储层保序，推荐根治）**：让 overgraph-storage 默认用 msgpack blob 编码 props 以保序（msgpackr 保序）。改动 `_serializeProps` 默认启用，或让 `upsertNode` 始终 msgpack 编码。风险：改默认存储格式，影响性能/兼容性，需充分测 storage-provider.spec 等。
- **方案 B（比较器层容忍）**：`toNodeNotation` 改用稳定键序 —— 但 TCK 期望声明顺序（非字典序），此方案需配合保存键序元数据，否则无法还原声明顺序。不推荐单用。

### 待办

## 2026-08-20 — ORDER BY UndefinedVariable 作用域追踪完成（commit 537b20f2）

### 迭代成果：with-orderBy 216/292（+42），UndefinedVariable 归零
- 新增 `_validateOrderByScope(query)`（executor-validators.ts，~195 行），在 `_validatePlan` 调用。
- **作用域模型**（关键、精确）：
  - MATCH/UNWIND 引入变量入 scope
  - WITH 子句**重置** scope = 投影表达式引用的**源变量** ∪ 投影别名
  - WITH 的 ORDER BY 合法作用域 = 源变量 ∪ 别名（非旧 scope！）
  - RETURN 的 ORDER BY 合法作用域 = 入 scope ∪ RETURN 别名
- **变量提取精度**（`_extractOrderByVars`）：排除属性名（`a.num`→`a`）、参数（`$x`）、map 字面量 key（`date({year:...})`→`year` 非变量）、函数名、关键字。
- **子句切分**（`_splitQueryClauses`）：字符串/括号/反引号感知，ORDER BY/SKIP/LIMIT 正确归属到所属 WITH/RETURN。

### 修复的坑（调试中发现的）
1. `ORDER BY` 独立成行时，`_splitQueryClauses` 正确并入前置 WITH（不是独立子句）。
2. map 字面量 key 误报：`duration({months:1})` 的 `months` 被当变量 → 加 `{...}` 剥离循环。
3. RETURN 别名引用：`RETURN r AS rel ORDER BY rel.id` 的 `rel` 需加入 effectiveScope。
4. **核心规则纠错**：WITH 的 ORDER BY 作用域是「投影源变量∪别名」，**不是**「旧 scope∪别名」——否则 [19] `me.age` 漏报。
