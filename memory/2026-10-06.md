### 本轮成果（4 个独立 bug 修复，4 次提交，全部零退化）

#### 1. WithWhere1 [3][4] — OPTIONAL free source 路由 + 匿名节点身份（第 62 次 `339c465d`）
- 根因 A：单 MATCH + OPTIONAL free source（`MATCH (other:B) OPTIONAL MATCH (a)-[r]->(other)`）被路由到 GE 主路径，GE 无法展开 free source（srcNodeIdx=-1），`a IS NULL` 永不成立。
- 根因 B：`_nodeIdxOf` 过滤 `k !== 'id'`，匿名节点 `(:B {id:2})` 的 keys 为空，塌缩到第一个同名 label 节点（idx 1）。
- 修复：`_optionalHasFreeSource` 检测（只认第一个 step 的 source；累积 OPTIONAL 链绑定 bound vars；排除复用 bound relationship 的反向查找）；`id` 纳入节点区分。

#### 2. WithWhere5 [1][2][3][4] — 字符串比较 + OR 三值逻辑（第 63 次 `02b27652`）
- 根因 A：GT/LT/GTE/LTE 用 `Number(actual) > Number(fv)`，`'text' > 'te'` 变成 `NaN > NaN` 破坏字典序。改用 `_compareValues`（三值逻辑，已 import）。
- 根因 B：`WITH ... WHERE A OR B` 被 `parseWhereClause` 的 `splitByTopLevelAndOr` 拆成 filters 数组后**丢失 OR 连接符**，`_withFilterKeepMask` 用 `every`（AND 语义）重复过滤，叠加在 whereBody pass 已正确保留的行上，把本该保留的 IntNode 过滤掉。修复：检测顶层 OR 时跳过 `_withFilterKeepMask`（whereBody pass 已正确处理）。

#### 3. WithWhere7 [3] — 变量可见性（顺带修复）
- 由 free source routing 修复连带解决。

#### 4. WithOrderBy1 [45] floats — 浮点排序（第 64 次 `27a48fb3`）
- 根因：`3.0`（integral float literal）被解析成 `{ __float: 3 }`（保留 Cypher Float 类型，用于 `1 / 2.0` 整数除法判定）。
- `_compareValues` 有 unwrap `__float`，但 `_compareOrderByValue`（ORDER BY）**没有**，`{__float:3}` 被当 object（type rank 0 = map）排到所有 number 前面。
- 修复：`_compareOrderByValue` 开头加 `__float` unwrap（镜像 `_compareValues`）。
- 这是**预先存在的 bug**（回退到 339c465d 和 7747516d 基线均 FAIL），非 with-where 改动引入。

### 关键教训
1. **`__float` 包装是双刃剑**：`_compareValues` 有 unwrap，但 `_compareOrderByValue`、`_orderByTypeRank` 等排序/比较路径必须同步 unwrap，否则 `{__float:3}` 被当 map/object，排序错乱。
2. **`_withFilterKeepMask` 用 `every`（AND）**：与 whereBody pass 双重过滤；当 WHERE 含顶层 OR 时必须跳过它，否则 OR 语义丢失。
3. **全量 clauses 单进程 cucumber 超时（900s 不够）**：改用**逐目录脚本**（每目录 timeout 180s）跑，16/17 目录快速定位。
4. **JSON 解析失败**：cucumber 的 ANTLR stderr 噪音会污染 stdout JSON；`--format json:temp/xxx.json` 在进程被 kill 时 0 字节不刷盘。逐目录 + `2>/dev/null` 更稳。

### 最后 1 个失败：graph [3] `properties()` on null（第 65 次 `8262a26d`）
- 根因：bare label-scan OPTIONAL（`OPTIONAL MATCH (n:Label)`，steps=[]）的绑定变量在 `om.variableName`，而 `_optionalHasFreeSource` 只遍历 `om.steps` 添加绑定，导致 label-scan OPTIONAL 的变量未被标记 bound。
- 后果：后续 `OPTIONAL MATCH (n)-[r]->()` 复用该变量被误判为 free source，路由到 cross-join，cross-join 在 source=null 时丢弃整行（而非产出 {n:null, r:null}）。
- 修复：`_optionalHasFreeSource` 循环里 `if (om.variableName) _boundSoFar.add(om.variableName)`。
- 这是**我之前 free-source routing 修复引入的回归**（基线 7747516d 正确返回 [{n:null,r:null}]）。
