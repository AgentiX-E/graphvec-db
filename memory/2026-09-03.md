### 剩余 1 个失败：`[7] toInteger on node property` — 根因已定位

**TCK 场景**：`MATCH (p:Person { name: '42' }) WITH * MATCH (n) RETURN toInteger(n.name) AS name`
- 期望 `[{"name":"42"}]`，实际 `[]`（0 行）

**根因**（已精确定位）：step-definition.ts 的 `having executed` 里"大整数精度保护"逻辑：
```js
if (typeof node[k] === 'string' && /^-?\d+$/.test(node[k])) {
  node[k] = Number(node[k])  // 把字符串 '42' 误转成数字 42
}
```
- `CREATE (:Person {name:'42'})` 的 `name='42'`（字符串）被误转成数字 `42`
- 本质：`parseQuery` 把**大整数字面量**（`4611686018427387905` → `{type:'STRING', value:'4611686018427387905'}`）和**字符串字面量**（`'42'` → `{type:'STRING', value:'42'}`）都存成 `{type:'STRING'}`，step-definition 无法区分

**parseQuery props 类型现状**（已用 diag-props.ts 验证）：
- `name: '42'` → `{type:'STRING', value:'42'}`
- `val: 42` → `{type:'NUMBER', value:42}`（**已经是数字**）
- `big: 4611686018427387905` → `{type:'STRING', value:'4611686018427387905'}`（**大整数存成 STRING 保精度**）
- `f: 3.14` → `{type:'NUMBER', value:3.14}`

**修复方向**（已明确，尚未实施）：
- 大整数与字符串字面量需区分。最佳：让大整数标记为独立类型（如 `{type:'BIGINT', value:'...'}`），字符串保持 `STRING`，step-definition 只在 `BIGINT`/大整数类型时才转 bigint，不再用"纯数字字符串"启发式误伤 `'42'`
- 相关位置：query-parser.ts line 603-614（createNodes props 格式转换）、line 1070-1072（`_parsePropValue` 或类似）、ast-to-plan-v2.ts line 2395-2397（大整数保持字符串精度）

### 关键教训
- JS `new RegExp('...\s...')` 字符串构造器里 `\s` 必须写 `\\s`（双反斜杠）；`/...\/ ` 正则字面量里 `\s` 单反斜杠即可。之前排查时误报了很多正则字面量，只有 `new RegExp('...')` 字符串构造器里的 `\s` 需要双反斜杠。
- `_deepStripInternal` 剥离 `__` 前缀内部字段；自定义标记（如 `__float`）必须加入白名单，否则 GE 路径会被剥离成空对象。
- `_fixScanLabel` 需同时修复顶层 scanLabel、optionalMatchSteps、multiMatch 三处的变量名误当标签问题。
- step-definition 的数字转换启发式（`/^-?\d+$/`）会误伤字符串字面量属性；根因是 parseQuery 未区分大整数（保精度 STRING）和真字符串（STRING）。
- 跨 MATCH 笛卡尔积（`MATCH (m) WITH * MATCH (n)`）的 `n` 绑定其实是**正确的**（诊断返回正确 1 行），TCK 0 行是 `name` 被误转数字 + 属性过滤 `filters=[]` 的连锁反应，不是执行层跨 MATCH bug。
